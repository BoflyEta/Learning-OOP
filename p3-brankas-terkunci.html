Brankas Terkunci

Data penting nggak boleh disentuh sembarangan. private field, get, dan set adalah cara class ngelindungin isinya sendiri.

Durasi: 120 menit Prasyarat: class & constructor (Pertemuan 2) Bahasa: JavaScript (ES6+)
1

Celah yang Kita Buka Sendiri

Coba bayangin bank nyimpen uang nasabah di atas meja terbuka di lobi — siapa aja yang lewat bisa ngambil atau nambah angka di buku catatan itu seenaknya. Nggak masuk akal, kan? Tapi itu persis yang kejadian kalau properti sebuah objek dibiarin publik gitu aja.

Solusi bank yang beneran adalah brankas: uang disimpan di ruang terkunci, dan satu-satunya cara masukin atau ngeluarin uang adalah lewat teller yang ikutin prosedur resmi — verifikasi identitas, catat transaksi, cek saldo cukup apa nggak. Nasabah nggak pernah langsung nyentuh brankasnya sendiri. Prinsip yang sama berlaku di kode: data penting disembunyikan, dan satu-satunya jalan masuk adalah lewat method yang udah punya aturan.

Properti saldo di sini publik — siapa aja bisa nimpanya langsung, tanpa lewat proses setor/tarik yang wajar.

tanpa-proteksi.js
class RekeningTanpaProteksi {
  constructor(pemilik, saldo) {
    this.pemilik = pemilik;
    this.saldo = saldo;
  }
}

const rek = new RekeningTanpaProteksi("Sari", 500000);
console.log("Saldo awal:", rek.saldo);

// Tidak ada yang mencegah baris ini:
rek.saldo = -999999999;
console.log("Saldo setelah diutak-atik dari luar:", rek.saldo);
Klik "Jalankan" untuk melihat betapa mudahnya data ini dirusak.

#saldo itu private field — cuma bisa diubah lewat method resmi di dalam class ini: setor() dan tarik(), keduanya udah ada aturannya.

rekening-bank.js
class RekeningBank {
  #saldo; // private field - hanya bisa disentuh dari dalam class ini

  constructor(pemilik, saldoAwal) {
    this.pemilik = pemilik;
    this.#saldo = saldoAwal > 0 ? saldoAwal : 0;
  }

  setor(jumlah) {
    if (jumlah <= 0) {
      console.log("Setor gagal: jumlah harus lebih dari 0");
      return;
    }
    this.#saldo += jumlah;
    console.log(`Setor ${jumlah} berhasil. Saldo sekarang: ${this.#saldo}`);
  }

  tarik(jumlah) {
    if (jumlah <= 0) {
      console.log("Tarik gagal: jumlah harus lebih dari 0");
      return;
    }
    if (jumlah > this.#saldo) {
      console.log("Tarik gagal: saldo tidak cukup");
      return;
    }
    this.#saldo -= jumlah;
    console.log(`Tarik ${jumlah} berhasil. Saldo sekarang: ${this.#saldo}`);
  }

  get saldo() {
    return this.#saldo;
  }
}

const rekening = new RekeningBank("Sari", 500000);
rekening.setor(200000);
rekening.tarik(1000000);   // ditolak, saldo tidak cukup
rekening.tarik(300000);
console.log("Saldo akhir (lewat getter):", rekening.saldo);

// Coba "akali" dari luar:
rekening.saldo = 999999999;
console.log("Saldo asli tetap aman:", rekening.saldo);
Klik "Jalankan" untuk membandingkan hasilnya.
Coba perhatiin baris terakhir: percobaan rekening.saldo = 999999999 nggak error, tapi juga nggak ngaruh apa-apa — soalnya saldo di sini cuma get (tanpa set), dan #saldo yang asli tersembunyi rapat di dalam class.
2

Getter & Setter: Pintu Baca dan Pintu Tulis

get bikin sebuah method bisa dibaca kayak properti biasa — tanpa tanda kurung — padahal di baliknya ada kode yang jalan. set ngelakuin hal serupa buat penulisan, dan di situlah tempat paling wajar buat naruh validasi.

Keduanya nggak melulu soal validasi — kadang dipakai buat ngitung nilai otomatis, kayak contoh berikut.

anatomi-getset.js
class Termometer {
  #celsius = 0;

  get celsius() {
    return this.#celsius;
  }

  set celsius(nilai) {
    this.#celsius = nilai;
  }

  // dihitung otomatis dari #celsius, bukan disimpan terpisah
  get fahrenheit() {
    return this.#celsius * 9 / 5 + 32;
  }

  set fahrenheit(nilai) {
    this.#celsius = (nilai - 32) * 5 / 9;
  }
}

const suhu = new Termometer();
suhu.celsius = 25;
console.log(`${suhu.celsius}°C = ${suhu.fahrenheit}°F`);

suhu.fahrenheit = 98.6;
console.log(`${suhu.fahrenheit}°F = ${suhu.celsius.toFixed(1)}°C`);
Klik "Jalankan" untuk melihat konversi otomatisnya.
Intinya gini: suhu.celsius = 25 keliatannya kayak ngisi properti biasa, tapi sebenarnya itu manggil method set celsius(). Dari luar, pemakainya nggak perlu tahu ada perhitungan di baliknya.

Encapsulation nggak selalu berarti "boleh dibaca, tapi divalidasi dulu". Kadang data harus disembunyikan total — nggak pernah diekspos ke luar sama sekali, kayak password. Contoh berikut sengaja nggak punya get password(): satu-satunya cara berinteraksi sama password adalah lewat method cekPassword(), yang cuma jawab benar/salah tanpa pernah bocorin nilai aslinya.

akun-password.js
class Akun {
  #password; // tidak ada getter — tidak pernah bisa dibaca dari luar

  constructor(username, password) {
    this.username = username;
    this.#password = password;
  }

  cekPassword(coba) {
    return coba === this.#password;
  }
}

const akun = new Akun("sari123", "rahasia99");
console.log(akun.cekPassword("salah"));       // false
console.log(akun.cekPassword("rahasia99"));   // true
console.log(akun.password);                   // undefined - memang tidak pernah ada jalannya
Klik "Jalankan" untuk melihat hasilnya.
Bandingin sama Termometer tadi: di sana get memang disediain karena celsius/fahrenheit wajar dibaca ulang. Di Akun, nggak ada get password() sama sekali — encapsulation di sini bukan cuma soal validasi tulis, tapi juga soal apa yang boleh dibaca.
3

Istilah yang Perlu Melekat

  • Private field (#nama) — properti yang cuma bisa dibaca/diubah dari dalam class itu sendiri. Kode di luar class nggak punya akses sama sekali.
  • Encapsulation (enkapsulasi) — istilah umum buat "membungkus dan melindungi" data kayak gini, salah satu dari empat pilar OOP yang udah dikenalin di Pertemuan 1.
  • get — nentuin cara membaca nilai, dipanggil tanpa tanda kurung kayak properti biasa.
  • set — nentuin cara menulis nilai; tempat yang wajar buat naruh pengecekan/validasi sebelum data bener-bener disimpan.
  • Data hiding — akibat langsung dari enkapsulasi: dunia luar nggak perlu (dan nggak bisa) tahu detail penyimpanan data di dalam objek.

Latihan: Produk dengan Harga Terlindungi

Coba lengkapi class Produk di bawah: harga disimpan sebagai private field #harga, dibaca lewat get harga(), dan ditulis lewat set harga() yang nolak nilai negatif atau bukan angka (cukup cetak pesan penolakan, jangan biarin nilainya lolos).

latihan-produk.js — bisa diedit
Lengkapi kode lalu klik "Jalankan".
kunci-jawaban.js
class Produk {
  #harga;

  constructor(nama, harga) {
    this.nama = nama;
    this.harga = harga;
  }

  get harga() {
    return this.#harga;
  }

  set harga(nilai) {
    if (typeof nilai !== "number" || nilai < 0) {
      console.log(`Harga ditolak: ${nilai} bukan angka valid atau negatif`);
      return;
    }
    this.#harga = nilai;
  }
}

const sepatu = new Produk("Sepatu Lari", 350000);
console.log(sepatu.harga);

sepatu.harga = -50000;
console.log(sepatu.harga);

sepatu.harga = "gratis";
console.log(sepatu.harga);

sepatu.harga = 300000;
console.log(sepatu.harga);

Latihan tambahan: lengkapi class AkunPengguna di bawah. #password nggak boleh punya getter sama sekali. cekPassword(coba) ngembaliin true/false. gantiPassword(lama, baru) cuma berhasil ngeganti kalau lama cocok sama password saat ini — kalau nggak cocok, cetak pesan gagal dan jangan ubah apa pun.

latihan-akun.js — bisa diedit
Lengkapi kode lalu klik "Jalankan".
kunci-jawaban.js
class AkunPengguna {
  #password;

  constructor(username, password) {
    this.username = username;
    this.#password = password;
  }

  cekPassword(coba) {
    return coba === this.#password;
  }

  gantiPassword(lama, baru) {
    if (lama !== this.#password) {
      console.log("Gagal ganti password: password lama salah");
      return;
    }
    this.#password = baru;
    console.log("Password berhasil diganti");
  }
}

const akun = new AkunPengguna("dewi22", "kucing123");
console.log(akun.cekPassword("salah"));
akun.gantiPassword("salahlagi", "baru123");
akun.gantiPassword("kucing123", "baru123");
console.log(akun.cekPassword("baru123"));
5

Cek Pemahaman

1. Kenapa #saldo dibikin sebagai private field, bukan properti biasa this.saldo?

Inilah inti encapsulation: data penting cuma boleh diubah lewat "pintu resmi" yang udah punya aturan.

2. Kalau kode di luar class nyoba rekening.saldo = 999999999, padahal saldo cuma diekspos lewat get (tanpa set), apa yang bakal kejadian?

Tanpa setter, percobaan nulis lewat nama itu percuma — nggak error, tapi juga nggak ngaruh.

3. Bedanya get sama set pada sebuah class itu apa sih?

Kayak di Termometer tadi: get itu baca (bahkan ngitung), set itu tulis (bahkan bisa konversi balik).

4. Di latihan class Produk, kenapa this.harga = harga di constructor tetap penting meski udah ada #harga?

Kalau constructor langsung nulis this.#harga = harga, validasi di setter bakal kelewat buat nilai pertama.

5. Di contoh class Akun (password), kenapa nggak dibikin get password()?

Beda sama Termometer yang wajar dibaca ulang, password justru harus disembunyikan total — encapsulation juga soal apa yang NGGAK boleh diekspos.

6. Di gantiPassword(lama, baru), kenapa kita tetap mewajibkan parameter lama, padahal di dalam class udah bisa langsung akses #password?

Encapsulation bukan cuma nyembunyiin data, tapi juga ngedesain "pintu resmi" mana yang boleh dipakai dan syarat apa yang harus dipenuhi sebelum data berubah.
Skor: 0 / 6 terjawab benar
6

Ringkasan Pertemuan 3

  • Properti publik bisa diubah siapa aja dari luar tanpa aturan — berbahaya buat data yang penting kayak saldo atau harga.
  • Private field (#nama) nyembunyiin data biar cuma bisa disentuh dari dalam class.
  • get baca nilai kayak properti biasa; set tulis nilai sekaligus jadi tempat validasi.
  • Ngisi private field sejak awal (di constructor) sebaiknya tetap lewat setter, biar validasi berlaku sejak data pertama masuk.
  • Encapsulation nggak selalu berarti "boleh dibaca setelah divalidasi" — kadang data kayak password harus disembunyikan total, tanpa getter sama sekali, dan cuma bisa "ditanya" lewat method kayak cekPassword().
Selanjutnya

Pertemuan 4 bakal bahas Inheritance — gimana caranya satu class bisa "mewarisi" properti dan method dari class lain, biar class-class yang mirip nggak perlu ditulis ulang dari nol.
