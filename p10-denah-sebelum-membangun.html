Denah Sebelum Membangun

Sebelum mulai ngoding proyek akhir, kita belajar dulu cara merencanakan: nemuin calon class dari deskripsi kebutuhan, terus gambar jadi diagram class sederhana.

Durasi: 120 menit Prasyarat: seluruh Modul 1–3 (Pertemuan 1–9) Bahasa: JavaScript (ES6+)
1

Ngoding Tanpa Rencana Itu Kayak Apa

Coba bayangin tukang bangunan yang langsung mulai kerja tanpa denah dari arsitek. Dia gali fondasi seenaknya, pasang tembok sambil mikir, terus baru sadar kamar mandinya kegedean, pintu kamar nabrak tembok, dan tangganya nggak nyampe ke lantai dua. Hasilnya? Bongkar-pasang ulang berkali-kali, buang waktu dan bahan bangunan sia-sia.

Nah, ngoding proyek besar tanpa rencana itu mirip banget. Kamu bisa aja langsung buka editor dan mulai nulis kode — dan di awal, kelihatannya jalan-jalan aja. Tapi begitu proyeknya membesar, biasanya kejadian yang sama kayak di Pertemuan 1 dulu: satu class ujung-ujungnya ngerjain semua hal sekaligus — nyimpen data, ngitung logika, ngurusin tampilan, validasi input — semua numpuk jadi satu, dan kodenya jadi berantakan susah dirawat.

Makanya, sebelum kita mulai ngoding proyek akhir kelas ini, kita perlu bikin "denah" dulu. Tapi ini beda sama blueprint yang kita bahas di Pertemuan 2 — di sana, blueprint itu class untuk satu jenis objek doang. Di sini, denah yang kita bikin itu untuk seluruh proyek: class apa aja yang dibutuhkan, dan gimana mereka saling berhubungan satu sama lain.

Gampangnya gini: arsitek nggak langsung nyuruh tukang gali tanah. Dia gambar denah dulu — ruang apa aja yang ada, di mana pintunya, gimana alurnya. Kita juga gitu: sebelum nulis class pertama, kita cari tahu dulu class apa aja yang bakal kita butuhkan.
2

Nemuin Calon Class dari Cerita

Ada teknik simpel banget buat nemuin calon class dari deskripsi kebutuhan: baca pelan-pelan, terus garis-bawahi dua jenis kata.

Kata benda (orang, barang, konsep) biasanya jadi calon class atau properti. Kata kerja (aksi yang dilakukan) biasanya jadi calon method. Sesederhana itu — coba kita praktikkan.

"Kita mau bikin aplikasi To-Do List sederhana. Aplikasi ini nyimpen banyak tugas. Setiap tugas punya judul, tenggat waktu, dan status (belum selesai / sudah selesai). Pengguna bisa nambah tugas baru, menghapus tugas, dan menandai tugas sebagai selesai. Pengguna juga pengen lihat daftar semua tugas yang belum selesai aja."

Coba kita bedah bareng. Kata benda utama yang muncul: "tugas" dan "daftar tugas" — dua-duanya cukup penting dan punya data sendiri, jadi keduanya layak jadi class. Kata benda kecil kayak "judul", "tenggat waktu", dan "status" itu bukan class, tapi jadi properti milik Tugas. Sementara kata kerja kayak "nambah", "menghapus", "menandai selesai", dan "menampilkan yang belum selesai" jadi calon method.

Hasil analisisnya kira-kira gini:

Class Tugas — properti: judul, tenggat, status. Method: tandaiSelesai().
Class DaftarTugas — properti: daftar (array berisi banyak Tugas). Method: tambah(), hapus(), tampilkanBelumSelesai().

Perhatiin: "menandai selesai" jadi method di dalam Tugas sendiri (soalnya yang berubah statusnya adalah si tugas itu), sementara "nambah" dan "menghapus" jadi method di DaftarTugas (soalnya yang ngurusin koleksi tugas adalah si daftar, bukan tugas satuan). Teknik kata benda→class, kata kerja→method ini nggak selalu 100% presisi, tapi udah cukup buat titik awal yang solid.

3

Dari Daftar ke Diagram Class Sederhana

Daftar class kayak di atas udah lumayan, tapi bakal lebih gampang dibaca kalau digambar. Kita pakai notasi diagram class super-simpel — bukan UML formal yang njelimet, cukup versi ringan yang gampang dipahami pemula: satu kotak per class, dibagi jadi tiga bagian — nama class di atas, daftar properti di tengah, daftar method di bawah.

DaftarTugas
- daftar: Tugas[]
+ tambah()
+ hapus()
+ tampilkanBelumSelesai()
punya banyak
Tugas
- judul: string
- tenggat: string
- status: string
+ tandaiSelesai()

Garis dengan panah kecil dan label "punya banyak" di antara dua kotak itu artinya: satu DaftarTugas bisa punya banyak Tugas di dalamnya (relasi ini sering disebut komposisi 1-ke-banyak). Diagramnya kebaca dari kiri ke kanan: "satu DaftarTugas punya banyak Tugas". Sesimpel itu — nggak perlu simbol UML yang ribet buat mulai merencanakan proyek kelas ini.

4

Dari Diagram ke Kerangka Kode

Sekarang bagian serunya: diagram di atas itu langsung bisa diterjemahkan jadi kode beneran. Kotak properti jadi field yang diisi di constructor, kotak method jadi method beneran di dalam class. Coba jalankan kodenya di bawah.

todo-list.js
class Tugas {
  #status = "belum selesai";
  constructor(judul, tenggat) {
    this.judul = judul;
    this.tenggat = tenggat;
  }
  tandaiSelesai() {
    this.#status = "selesai";
  }
  get status() {
    return this.#status;
  }
}

class DaftarTugas {
  #daftar = [];
  tambah(tugas) {
    this.#daftar.push(tugas);
  }
  hapus(index) {
    this.#daftar.splice(index, 1);
  }
  tampilkanBelumSelesai() {
    this.#daftar
      .filter(t => t.status === "belum selesai")
      .forEach(t => console.log(`- ${t.judul} (tenggat: ${t.tenggat})`));
  }
}

const daftar = new DaftarTugas();
daftar.tambah(new Tugas("Belajar OOP", "30 Agustus"));
daftar.tambah(new Tugas("Kerjain PR", "1 September"));
daftar.tampilkanBelumSelesai();
Klik "Jalankan" untuk melihat hasilnya.
Perhatiin nih: #status di Tugas sengaja dibuat private field dengan get status() buat bacanya — persis konsep encapsulation dari Pertemuan 3. Dan strukturnya persis kayak yang kita gambar di diagram tadi: kotak properti di DaftarTugas jadi #daftar = [], kotak method tambah()/hapus()/tampilkanBelumSelesai() jadi method beneran. Diagram bukan cuma gambar hiasan — dia peta langsung ke kode.

Latihan: Rencanain Sendiri — Perpustakaan Sederhana

Giliran kamu sekarang. Ini deskripsi kebutuhannya:

"Aplikasi Perpustakaan Sederhana ini nyimpen banyak buku. Setiap buku punya judul, penulis, dan status pinjam (dipinjam / tersedia). Admin bisa menambah buku baru, meminjamkan buku (kalau statusnya tersedia), dan mengembalikan buku (mengubah status jadi tersedia lagi)."

Coba identifikasi sendiri: kata benda "buku" jadi class Buku, dengan properti judul, penulis, dan status. Kata kerja "meminjamkan" dan "mengembalikan" jadi method pinjam() dan kembalikan(). Sekarang lengkapi skeleton class Buku di bawah ini sesuai TODO-nya.

Lengkapi kode lalu klik "Jalankan".
kunci-jawaban.js
class Buku {
  #status = "tersedia";
  constructor(judul, penulis) {
    this.judul = judul;
    this.penulis = penulis;
  }
  pinjam() {
    if (this.#status === "tersedia") {
      this.#status = "dipinjam";
      console.log(`${this.judul} berhasil dipinjam`);
    } else {
      console.log(`${this.judul} gagal dipinjam, sedang dipinjam orang lain`);
    }
  }
  kembalikan() {
    this.#status = "tersedia";
    console.log(`${this.judul} sudah dikembalikan`);
  }
  get status() {
    return this.#status;
  }
}
const buku1 = new Buku("Laskar Pelangi", "Andrea Hirata");
console.log(buku1.status);
buku1.pinjam();
buku1.pinjam();
buku1.kembalikan();
console.log(buku1.status);
6

Cek Pemahaman

1. Kenapa sih penting bikin "rencana" dulu sebelum langsung ngoding proyek besar?

Sama kayak tukang bangunan tanpa denah arsitek — bisa jalan di awal, tapi berujung bongkar-pasang ulang begitu proyeknya membesar.

2. Dari kalimat "Setiap mobil punya plat nomor dan warna. Montir bisa mengecat ulang mobil dan mengganti plat nomornya", kata mana yang paling tepat jadi calon method?

Kata kerja (aksi) jadi calon method; "mobil" jadi class, "plat nomor" dan "warna" jadi properti.

3. Diagram class sederhana yang kita pakai di sheet ini dibagi jadi tiga bagian dalam satu kotak. Urutannya gimana?

Nama class di atas biar gampang dikenali, properti di tengah, method di bawah — urutan ini yang bikin diagram gampang dibaca sekilas.

4. Garis dengan label "punya banyak" antara DaftarTugas dan Tugas itu artinya apa?

Diagramnya kebaca dari kiri ke kanan: satu DaftarTugas punya banyak Tugas — makanya di dalam DaftarTugas ada array untuk nyimpen koleksi Tugas.

5. Di contoh class Tugas, kenapa #status dibikin private field, bukan properti biasa this.status?

Ini persis konsep encapsulation dari Pertemuan 3 — data penting cuma boleh diubah lewat "pintu resmi" yang udah punya aturan.

6. Deskripsi kebutuhan: "Aplikasi ini nyimpen banyak pelanggan. Setiap pelanggan punya nama dan nomor telepon." Class apa yang paling tepat dijadikan calon class utama?

"Pelanggan" adalah kata benda utama yang punya data sendiri (nama, nomor telepon) — itulah kandidat class paling tepat, sementara "nama" dan "nomor telepon" jadi properti miliknya.
Skor: 0 / 6 terjawab benar
7

Ringkasan Pertemuan 10

  • Rencana dulu sebelum ngoding mencegah satu class ujung-ujungnya ngerjain kebanyakan hal sekaligus begitu proyek membesar.
  • Teknik nemuin calon class: kata benda → class/properti, kata kerja → method. Baca deskripsi kebutuhan pelan-pelan, terus garis-bawahi keduanya.
  • Diagram class sederhana = kotak berisi nama class, daftar properti, daftar method, dihubungkan garis relasi (misalnya "punya banyak" untuk komposisi 1-ke-banyak).
  • Diagram itu bukan cuma gambar — dia langsung bisa diterjemahkan jadi kerangka kode class beneran: kotak properti jadi field, kotak method jadi method.
