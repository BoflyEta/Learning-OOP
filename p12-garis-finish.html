Garis Finish

Sesi terakhir nih — belajar cara review kode kayak seorang profesional, gimana cara presentasiin proyek, dan satu kuis besar yang ngerangkum seluruh perjalanan dari Pertemuan 1.

Durasi: 120 menit Prasyarat: Pertemuan 11 (Implementasi Proyek) Bahasa: JavaScript (ES6+)
1

Kenapa Code Review Itu Penting

Coba bayangin kamu abis nulis tulisan panjang — tugas, artikel, apa aja — terus mau langsung dikirim tanpa dibaca ulang sama orang lain. Padahal biasanya, begitu ada teman yang baca draftnya, dia bisa nemu typo atau lubang logika yang kamu sendiri udah kelewat lihat. Bukan karena kamu ceroboh, tapi karena kamu udah kelamaan mantengin tulisan itu sendiri — matamu udah "terbiasa" sama kesalahannya sampai nggak keliatan lagi.

Code review kerjanya persis gitu. Sebelum kode "dikirim" — dipakai orang lain, digabung ke proyek utama, atau di-submit sebagai tugas — ada baiknya orang lain (atau bahkan dirimu sendiri, dengan mata yang lebih segar) baca dulu dan nyari hal-hal yang mungkin kelewat.

Di dunia kerja beneran, ini bukan basa-basi — hampir semua kode yang ditulis programmer di sebuah tim itu wajib direview orang lain dulu sebelum digabung ke proyek utama. Bukan karena nggak percaya, tapi karena review itu jaring pengaman kedua yang nangkep hal-hal yang mungkin kelewat sama penulisnya sendiri.

3

Contoh Review: Before / After

Sekarang coba liat kode beneran yang "berbau" (dalam istilah review sering disebut code smell), terus gimana hasilnya setelah direview dan direfactor pakai konsep-konsep yang udah kita pelajari sepanjang course ini.

Perhatiin dua masalahnya: gaji publik dan gampang dirusak jadi negatif, terus satu fungsi ngerjain tiga hal sekaligus — cetak info, hitung bonus, kirim email.

pegawai-berbau.js
class Pegawai {
  constructor(nama, gaji) {
    this.nama = nama;
    this.gaji = gaji;
  }
}
const p1 = new Pegawai("Sari", 5000000);
p1.gaji = -999999999;
console.log(p1.gaji);

function cetakInfoDanHitungBonusDanKirimEmail(pegawai) {
  console.log(pegawai.nama);
  const bonus = pegawai.gaji * 0.1;
  console.log("bonus:", bonus);
  console.log("(pura-pura kirim email ke " + pegawai.nama + ")");
}
cetakInfoDanHitungBonusDanKirimEmail(p1);
Klik "Jalankan" untuk melihat betapa berantakannya ini.
Bau yang ketauan: gaji nggak punya perlindungan sama sekali, jadi bisa ditimpa jadi angka negatif segede itu tanpa ada yang nyegah. Terus cetakInfoDanHitungBonusDanKirimEmail — dari namanya aja udah ketauan dia ngerjain tiga hal berbeda dalam satu fungsi, yang bikin dia susah dites satu-satu dan susah dipakai ulang cuma sebagiannya aja.

#gaji sekarang private dengan validasi, dan tiap method cuma ngerjain satu hal — pola yang udah kita pelajari dari Pertemuan 3 sampai sekarang.

pegawai-rapi.js
class PegawaiRapi {
  #gaji;
  constructor(nama, gaji) {
    this.nama = nama;
    this.#gaji = gaji > 0 ? gaji : 0;
  }
  get gaji() { return this.#gaji; }
  hitungBonus() { return this.#gaji * 0.1; }
  cetakInfo() { console.log(`${this.nama} - gaji: ${this.#gaji}`); }
  kirimEmail() { console.log(`(pura-pura kirim email ke ${this.nama})`); }
}
const p2 = new PegawaiRapi("Sari", 5000000);
p2.gaji = -999999999;
console.log(p2.gaji);
p2.cetakInfo();
console.log("bonus:", p2.hitungBonus());
p2.kirimEmail();
Klik "Jalankan" untuk membandingkan hasilnya.
Perhatiin baris p2.gaji = -999999999: percobaan ini diabaikan diam-diam — persis kayak yang kita pelajari di Pertemuan 3, soalnya #gaji asli udah divalidasi sejak constructor dan cuma diekspos lewat get tanpa set. Terus tiap method sekarang cuma ngerjain satu hal aja (single responsibility) — cetakInfo(), hitungBonus(), dan kirimEmail() masing-masing berdiri sendiri, jadi lebih gampang dites dan dipakai ulang.

Latihan: Jadi Reviewer, Terus Refactor Sendiri

Sekarang gantian kamu yang jadi reviewer sekaligus yang ngerjain refactor-nya. class Produk di bawah ini masih berbau: properti publik semua, dan method kurangiStok belum ada validasinya. Lengkapi jadi private field + validasi, persis pola yang barusan kita liat.

latihan-produk.js — bisa diedit
Lengkapi kode lalu klik "Jalankan".
kunci-jawaban.js
class Produk {
  #harga;
  #stok;
  constructor(nama, harga, stok) {
    this.nama = nama;
    this.#harga = harga > 0 ? harga : 0;
    this.#stok = stok >= 0 ? stok : 0;
  }
  get harga() { return this.#harga; }
  get stok() { return this.#stok; }
  kurangiStok(jumlah) {
    if (jumlah > this.#stok) {
      console.log("Gagal: stok tidak cukup");
      return;
    }
    this.#stok -= jumlah;
  }
  infoProduk() {
    console.log(`${this.nama} - Rp${this.#harga} (stok: ${this.#stok})`);
  }
}
const produk = new Produk("Kaos", 75000, 10);
produk.infoProduk();
produk.kurangiStok(3);
produk.infoProduk();
produk.kurangiStok(100);
5

Cara Presentasiin Proyekmu

Kode yang bagus itu satu hal, tapi bisa jelasin proyekmu ke orang lain itu skill yang sama pentingnya. Coba ikutin lima langkah ini pas presentasi proyek akhir.

  1. 1

    Masalah apa yang proyek ini selesaikan
    Kasih konteks singkat dulu — orang yang dengerin belum tentu tau kenapa proyekmu ini dibutuhkan sebelum kamu jelasin.

  2. 2

    Struktur class-mu
    Bisa tunjukin diagram class sederhana kayak yang dibikin di Pertemuan 10 — class apa aja yang ada, dan gimana mereka berhubungan (inheritance, komposisi, dll).

  3. 3

    Demo singkat
    Jalanin fitur utama langsung di depan, jangan cuma diceritain. Liat kode jalan itu jauh lebih meyakinkan daripada cuma dibacain.

  4. 4

    Tantangan yang ditemuin dan gimana cara ngatasinnya
    Misalnya bug this ilang, lupa new, atau error lain dari Pertemuan 11 — cerita gimana kamu nemuin dan nyelesaininnya justru nunjukin kamu paham, bukan cuma nyontek.

  5. 5

    Kalau ada waktu lebih, mau dikembangin ke mana lagi
    Nggak ada proyek yang beneran "selesai total" — nunjukin kamu udah mikirin langkah berikutnya itu nilai plus.

6

Kuis Tantangan Akhir

Ini kuis paling gede di seluruh course — delapan soal yang ngerangkum perjalanan dari Pertemuan 1 sampai sekarang. Coba inget-inget lagi analogi-analogi yang udah kita pakai sepanjang jalan.

1. Kapan sebaiknya kita cukup pakai object literal ({ ... }) biasa, dan kapan sebaiknya naik level ke class?

Inget motor "Vario" di Pertemuan 1 — object literal udah cukup buat satu motor. Tapi begitu kita butuh bikin banyak motor dengan pola yang sama, class (cetak biru) jadi jauh lebih masuk akal daripada nulis ulang tiap objek satu-satu.

2. Analogi "kotak perkakas yang terkunci" itu ngegambarin pilar OOP yang mana, dan kenapa analoginya pas?

Persis kayak brankas di Pertemuan 3: orang luar nggak bisa ngubek isinya sembarangan, harus lewat method resmi yang udah tervalidasi.

3. Di analogi "resep turunan" (resep Kue Dasar diwariskan ke Kue Coklat), apa peran extends dan super()?

Sama kayak resep Kue Coklat yang nggak perlu nulis ulang semua langkah dasar bikin adonan — tinggal "warisi" resep dasarnya (extends), lalu jalanin dulu bagian dasarnya (super()) sebelum nambah langkah spesialnya sendiri.

4. Kenapa aba-aba balapan ("mulai!") jadi analogi yang pas buat polymorphism?

Ini juga yang kejadian di Pertemuan 11: array campuran Tugas dan TugasPenting, dipanggil tandaiSelesai() yang sama, tapi hasilnya beda tergantung objeknya.

5. Analogi "remote TV" buat abstraction artinya kita cukup pencet tombol power tanpa tau rangkaian di baliknya. Di kode, gimana bentuk konkretnya (misalnya lewat abstract class pattern)?

Inget "inspektur bangunan yang nggak pernah dateng" di Pertemuan 7 — abstract class pattern mastiin kontrak (kayak method luas()) wajib dipenuhi, jadi kesalahan nggak diam-diam kelewat.

6. Apa beda utama antara properti/method static dengan properti/method biasa (instance), dan kenapa this bisa "kehilangan nametag"-nya?

Dua analogi Pertemuan 8 sekaligus: static = papan pengumuman pabrik (milik pabriknya, bukan satu produk doang), dan this yang lepas = nametag karyawan yang kecopot pas method-nya dipisah dari objeknya.

7. Kapan pola Factory lebih masuk akal dipakai dibanding manggil new langsung satu-satu?

Sama kayak Singleton yang mastiin cuma ada satu "kantor pusat" di seluruh aplikasi — keduanya design pattern yang dipakai kalau beneran nyelesain masalah nyata, bukan cuma biar keliatan rapi.

8. Kenapa merencanakan dulu (kayak bikin denah di Pertemuan 10) dan mereview kode sebelum "dikirim" itu sama-sama penting, padahal keduanya bukan proses "ngoding" secara langsung?

Ini benang merah dari Pertemuan 10, 11, dan 12: denah sebelum membangun, bangun bertahap per checkpoint, lalu review sebelum dianggap selesai — tiga tahap yang saling melengkapi, bukan langkah yang bisa dilewatin.
Skor: 0 / 8 terjawab benar

Ringkasan Pertemuan 12

  • Code review itu jaring pengaman kedua — kayak minta teman baca draft tulisanmu sebelum dikirim, dia bisa nemu hal yang udah kelewat kamu lihat sendiri.
  • Checklist review yang paling sering dipakai: properti publik yang seharusnya private, method yang ngerjain lebih dari satu hal, kode yang di-copy-paste, penamaan yang nggak jelas, dan validasi yang bocor.
  • Refactor Pegawai jadi PegawaiRapi nunjukin gimana private field + validasi + single responsibility bikin kode jauh lebih aman dan gampang dites.
  • Presentasi proyek yang baik nyeritain masalah, struktur, demo, tantangan, dan rencana ke depan — bukan cuma mbacain kode baris per baris.
  • Dan yang paling penting: perjalanan kita dari object literal di Pertemuan 1 sampai design pattern di Pertemuan 9, dari nulis kode asal sampai belajar merencanakan (Pertemuan 10), membangun bertahap (Pertemuan 11), dan mereview kode kayak profesional (Pertemuan 12) — itu semua satu paket keterampilan yang saling ngedukung.
